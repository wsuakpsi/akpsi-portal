This project started from a gap analysis comparing the codebase against the reference spec, then broke the fixes into 8 phases. **All 8 phases are done.** This file is the handoff for whoever picks up real-world testing and deployment next — see "All 8 phases are now done" near the bottom for what's actually left.

## ⚠️ Read this before doing anything

1. **Live database, no local option.** There is no Docker/local Postgres in this environment (`supabase start` will fail). All schema work happens directly against the linked live Supabase project (`rmqgnapkcfbcksbrgnor`, org `wsuakpsi's Project`) via `supabase db push` / `supabase db query --linked "<sql>"`. There is no sandbox — be careful, and check existing data before backfills or destructive-looking migrations (see the proof_url backfill in migration 0004 for the pattern: don't silently fabricate data, use an explicit sentinel and say so).
2. **AWS credentials in this environment point to an unrelated account.** Running `aws sts get-caller-identity` here resolves to what looks like a work/employer account (stacks named `sdp-waf-dev`, `sdp-cdn-prod`, `EnterpriseBasicAuth`, etc.) — **not** a dedicated AKPsi account. Do not run `aws`/`cdk`/`sam` deploy commands against it. The nightly-sync cron (Phase 2) is written as code + a CloudFormation reference template but deliberately **not deployed**. If a later phase needs real AWS infra, stop and ask the user which account/credentials to use.
3. **No Lambdas are actually deployed anywhere yet.** All 9 Lambda functions in `lambdas/src/` are real, tested-by-syntax-check code, but there's no API Gateway in front of them. `.env.example` lists all the `VITE_*_URL` variables the frontend expects — they're currently unset in `.env.local`. This means true end-to-end testing (click a button, watch a real HTTP call succeed) isn't possible until someone deploys them. Verification in this project has topped out at: `npm run build` passes, `node --check` on every Lambda file, dynamic import resolves each `handler` export, dev server boots with a clean console.
4. **No test account passwords.** `scripts/seed-eboard.mjs` looks up a *pre-existing* Supabase Auth user by email — it doesn't create one with a known password. Can't log into the app to click-test flows without the user's help.

### Phase 1 — Schema & DB foundation ✅
Migrations `0003`–`0007` (all applied live, verified via `supabase migration list`):

**Gotchas hit and resolved:**
- `supabase db push` initially failed with `type "member_role" already exists` — the live DB had migrations 0001/0002 applied manually (SQL editor) before the CLI was ever linked, so the CLI's migration-history table didn't know about them. ### Phase 2 — Security fix + Sheets Archive tab ✅
This phase expanded a lot: the original ask was "stop shipping the Supabase service-role key to the browser for Sheets sync," but auditing turned up that **none of the 7 original Lambdas verified caller identity at all** — anyone with the API Gateway URL could call `postManualPointAdjustment` etc.

- **New `lambdas/src/lib/auth.js`** — `requireEboardCaller(event)` and `requireSelfOrEboardCaller(event, subjectMemberId)`. Both verify `Authorization: Bearer <supabase_access_token>` via `supabase.auth.getUser(token)`, then look up the caller's `members` row, reject suspended accounts, and (for the eboard variant) require `role='eboard'`.
- **`lambdas/src/lib/httpResponse.js`** rewritten — the old unauthenticated `wrapHandler` is gone (was dead code once everything needed auth). Now `wrapEboardHandler(coreFn, extractArgs)` and `wrapAuthedHandler(coreFn, extractArgs, getSubjectMemberId)`, both passing `extractArgs(payload, caller)` — **`caller.id` should always be used for "who did this" fields** (`createdBy`, `reviewedBy`, etc.), never trust the request body for that. This closed a real bug: `postManualPointAdjustment` and `reviewMissingMeetingForm` used to trust a client-supplied actor id.
- All 7 original Lambdas updated to use one of these wrappers. See `lambdas/README.md`'s "Authentication" section for the full breakdown of which Lambda uses which tier.
- **New `src/lib/lambdas.js`** (frontend) — `callLambda(url, body)` helper: pulls the current Supabase session token and POSTs with the `Authorization` header. Every phase since has used this for wiring UI to Lambdas.
- `SheetsSync.jsx` rewritten — no more `VITE_SHEETS_SYNC_SERVICE_ROLE_KEY` env var (the actual vulnerability); uses `callLambda` + looks up the active semester itself via the existing `getActiveSemester()` query helper.
- `syncToGoogleSheets.js` — tab naming changed from "one tab per semester name" to a fixed `Current Semester` tab (matches spec 14.2), plus an `{archive: true}` option that appends a timestamped snapshot to a new `Archive` tab. **Nothing calls this with `archive: true` yet — that's Phase 5's job**, when `calculateEndOfSemesterStanding` locks results.
- New `lambdas/src/nightlySheetsSync.js` — unauthenticated entrypoint meant for an EventBridge schedule (no human session to check). New `lambdas/infra/nightly-sheets-sync.template.yaml` — CloudFormation reference, **not deployed** (see AWS warning above).
- `.env.example` now lists every `VITE_*_URL` var needed by every Lambda that's been wired up so far.

### Phase 5 — Complete standing calculation ✅
`lambdas/src/calculateEndOfSemesterStanding.js` now implements all three checks from spec 5.2, gated by the double-run guard, and wires notifications + the Sheets archive.

- **New `fetchStandingAttendanceData` in `lambdas/src/lib/pointsAggregation.js`** — one query pass returning `totalEvents` (non-cancelled events this semester), `requiredEventIds` (non-cancelled + `is_required`), and per-member `attendedByMember`/`excusedCountByMember`/`excusedEventsByMember` maps. Deliberately built off the generic `events`/`attendance`/`missing_meeting_forms` tables, **not** `meeting_attendance` — `meeting_attendance` rows are only ever written by `reviewMissingMeetingForm`'s upsert-to-`excused` and the eboard Attendance page's manual correction form, so it isn't a reliable per-member "did they show up" source and nothing seeds `present` rows on real check-in. `attendance` is populated by every real check-in (QR or manual) regardless of event category, which is what spec 5.2 checks 2 and 3 actually key off ("required events... including meetings").
- **Check 2 (attendance %)** — `attended / totalEvents >= 0.55`, with `totalEvents === 0` treated as a pass (nothing to fail against yet).
- **Check 3 (absences)** — `excusedAbsences` = count of approved `missing_meeting_forms` (already excludes `voided` by construction, since cancellation flips `approved → voided`); `unexcusedAbsences` = required non-cancelled events with neither an attendance row nor an approved form for that specific event. Passes if `excused <= 2 && unexcused <= 1`.
- **Double-run guard** — checks `semesters.calculated_at` before running; if set and the payload's `confirm` isn't `true`, returns `{ success: false, error: 'already_calculated', calculatedAt }` instead of running. Frontend catches that exact error string and re-prompts with `confirm: true`.
- **Sheets archive** — calls `syncToGoogleSheets(semesterId, { archive: true })` (the core function, in-process, service-role already available) right after `calculated_at` is set. Its result is returned under `sheetsSync` but a sheets failure does **not** fail the whole calculation — `calculated_at` and notifications have already landed by that point and there's no transaction wrapping this, so surfacing the sheets error without pretending the calculation itself failed is the more honest result.
- **Notifications to everyone** — every active/probation brother gets a result notification now (previously only nobody did), regardless of pass/fail.
- **⚠️ Behavior change from the pre-Phase-5 code, worth flagging explicitly**: the old version auto-flipped `member.status` to `'probation'` on a failed calculation. **Removed.** Spec 5.1 ("Status changes... are manual E-Board decisions... The system does not automatically change member status") and spec 10.3 step 6 ("E-Board then manually updates `member.status` based on results. System does not auto-change status.") are both unambiguous on this, and it directly contradicts what the code was doing — this looks like a leftover from before the gap analysis rather than an intentional deviation. The Lambda now only returns each member's `standing` (`'good'` / `'probation'`) and per-check breakdown; nothing writes to `members.status`. Phase 6's status-change control (`BrotherDetail.jsx`) is the only place that should ever set it now.
- **UI** — `src/portals/eboard/pages/Points.jsx` (renamed heading to "Points & Standing") gained a "Calculate Standing" card and a results table (per-brother pass/fail per check, threshold type, points/attendance/absence figures). Re-run confirmation uses the same `window.confirm` pattern as `EventDetail.jsx`'s cancel/complete actions, matching the rest of the codebase rather than introducing a new modal component.
- **New `.claude/launch.json`** (untracked, local dev tooling only) — added an `eboard-dev` config (`npm run dev:eboard`, port 5180) so the dev server can be previewed in-browser. Not committed to git, same as the rest of `.claude/`.
- **Verification ceiling reached, same as every prior phase**: `npm run build` passes, `node --check` on every Lambda file including the new/edited ones, dynamic `import()` confirms both `calculateEndOfSemesterStanding.js` and `syncToGoogleSheets.js` still resolve their `handler` exports (no circular-import issue from the new in-process call), dev server boots with a clean console. **Could not click-test the actual calculation** — no deployed Lambda, no test login (same blockers as every phase before this one).

### Phase 7 — Brother Improvement Plans (BiP) ✅
Schema was already fully ready (Phase 1, migration 0007) — this was pure UI work across both portals.

- **Eboard creation form** (`CreateBipForm` in `BrotherDetail.jsx`) — `description`, `requirements`, `due_date`, direct Supabase insert (RLS `bip_insert_eboard` permits it), plus a `notifications` insert on creation. `BrotherDetail` now takes a `profile` prop (passed down from `EboardRouter` in `src/portals/eboard/index.jsx`, which already had it available but wasn't forwarding it to this route) so `created_by` can be the actual signed-in caller's id rather than something faked.
- **⚠️ Corrected a mistake in this handoff's own Phase 7 plan**: the write-up above said escalation "needs no note per the constraint." That's wrong — re-reading the actual migration 0007 text, `check (status = 'open' or resolution_note is not null)` requires a non-null `resolution_note` for **any** non-open status, escalated included, not just resolved. Spec 9's prose only mentions a note for the resolved case, but the live DB constraint is stricter than the prose and the DB is what actually gets enforced. Built `BipActions` to require a note for both resolve and escalate, so a real escalation attempt without one doesn't 400 against the constraint.
- **Brother-facing read-only view** — new "Improvement plans" card in `src/portals/brother/pages/Profile.jsx`, queries `brother_improvement_plans` scoped to `member_id = profile.id` (RLS `bip_select` already restricts to own rows, so no extra access-control logic needed client-side). Shows description, requirements, due date, status, and resolution/escalation note once present.
- **Not scoped to the active semester** in either portal — BiPs persist across semesters per spec 9.4/10.2 until resolved or escalated, so both queries just filter by `member_id` and order by `created_at`, no `semester_id` involved (the table doesn't even have that column).
- `due_date` is rendered as the raw `YYYY-MM-DD` string rather than through the existing `formatDate` helper — `formatDate` does `new Date(iso).toLocaleDateString(...)`, and a bare date-only string parsed that way is UTC midnight, which can display as the *previous* day in a negative-UTC-offset timezone. Nothing else in the app renders a pure `date` column today (everything else using `formatDate` is a `timestamptz`), so there was no existing convention to break by sidestepping it here.
- **Verification ceiling**: same as every phase — `npm run build`, dev server clean console (both `Profile.jsx` and `BrotherDetail.jsx` reload and transform with no errors), no test login so the actual create/resolve/escalate flows couldn't be click-tested against real data.

## Quick reference

- **Migrations applied so far**: `0001`–`0012`, all confirmed live via `supabase migration list` (all show matching `local`/`remote` versions).
- **Auth pattern for any new Lambda**: use `wrapEboardHandler` or `wrapAuthedHandler` from `lambdas/src/lib/httpResponse.js`, never the bare handler pattern — there's no RLS backstop since every Lambda runs with the service-role key.
- **Frontend pattern for calling any Lambda**: `callLambda(url, body)` from `src/lib/lambdas.js`, url from an env var following the `VITE_<THING>_URL` naming already established in `.env.example`.
- **Testing ceiling**: `npm run build`, `node --check` on Lambda files, dynamic `import()` to confirm handlers resolve, and `preview_start`/browser console checks for the dev server. No real login, no deployed Lambdas, no local DB — full E2E is not possible from this environment as currently configured.
